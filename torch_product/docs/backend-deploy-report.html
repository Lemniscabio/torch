The architecture, on one page

Before any commands, here’s the picture we were aiming at. The frontend was already live on Vercel; the backend was a Node/Express + Prisma + Postgres app that needed a home. The full intended architecture looks like this:

Frontend (Vercel) ─ Next.js, public web app │ │ HTTPS, JWT in Authorization header ▼ Backend (Cloud Run) ─ Express + Prisma │ ├─→ Cloud SQL ─ managed Postgres (private socket) ├─→ Secret Manager ─ DATABASE_URL, JWT_SECRET (read at boot) └─→ Cloud Logging ─ stdout/stderr captured automatically Artifact Registry ─ holds the Docker image Cloud Build ─ builds image from source, one-shot Deferred for later: Cloud Run Worker ─ PDF generation Cloud Tasks ─ queue for the worker Cloud Storage ─ stores generated PDFs Firebase Auth ─ to replace the current bcrypt+JWT setup

This piece covers everything in the first block. The deferred items (PDF generation, queue, storage, Firebase auth swap) are left for another writeup.

Why Cloud Run

The first decision was where the backend should run. A few options were on the table:

OptionWhy we passed
GCE VMPay for an idle box 24/7. Manual OS patching, manual scaling. No upside for a low-traffic API.
App EngineOlder, opinionated, slower to ship a custom Docker image. Cloud Run is essentially its modern replacement.
GKE (Kubernetes)Massive overkill for one service. Would need to learn ops we don’t need yet.
Cloud RunContainer in, URL out. Scales to zero, HTTPS for free, autoscaling, pay-per-request. Perfect for an API with bursty/low traffic.

The trade-off you accept with Cloud Run is a cold start: if no traffic has hit the service for a few minutes, the next request waits ~1–2 seconds while a container spins up. For a B2B tool with small user counts, that’s acceptable. If it becomes a problem later, we set --min-instances=1 and the cold start disappears (at the cost of ~$5–10/mo for an always-warm idle container).

Step 1 — Project, auth, region

We started by pointing gcloud at the right project and region. The project ID was an auto-generated one (project-688a4c78-5d5b-45b3-b5d) inside the lemnisca.bio org, with billing already enabled.

gcloud auth login
gcloud config set project project-688a4c78-5d5b-45b3-b5d
gcloud config set run/region us-central1
gcloud config set compute/region us-central1

Region choice: us-central1 because it’s the cheapest and oldest GCP region, has every service available, and there’s no latency-sensitive workload that demands somewhere closer. If our users were primarily in India, we’d use asia-south1. They’re not, so we don’t.

Step 2 — Enabling the APIs

GCP services are off by default until you turn them on per-project. We need six of them:

gcloud services enable \
  run.googleapis.com \
  sqladmin.googleapis.com \
  artifactregistry.googleapis.com \
  secretmanager.googleapis.com \
  cloudbuild.googleapis.com \
  compute.googleapis.com
APIWhy we need it
runCloud Run itself
sqladminCloud SQL — managed Postgres
artifactregistryStores the Docker image
secretmanagerStores DB URL + JWT secret
cloudbuildBuilds the image from source
computeProvides the default service account Cloud Run runs as

Step 3 — Cloud SQL: managed Postgres

Cloud Run is stateless. Containers come and go on every deploy and every scale event, so the database can’t live inside them. We provisioned the smallest possible Postgres 16 instance:

gcloud sql instances create torch-db \
  --database-version=POSTGRES_16 \
  --edition=ENTERPRISE \
  --tier=db-f1-micro \
  --region=us-central1 \
  --storage-size=10GB \
  --storage-type=SSD \
  --storage-auto-increase \
  --backup \
  --backup-start-time=03:00

Notes on each flag:

  • db-f1-micro — shared-core, ~$8/mo. Fine for dev and early users; trivially upgraded later.
  • --storage-auto-increase — saves you from ever having to manually resize when the DB fills up.
  • --backup --backup-start-time=03:00 — daily automated backups at 3am, retained seven days by default. Free.

After the instance was up we created the database and a Postgres user:

gcloud sql databases create torch --instance=torch-db
gcloud sql users create torch --instance=torch-db --password=<strong-password>
Two layers of credentials

This step creates a Postgres-level user and password. That’s separate from the GCP-level IAM that controls whether something is even allowed to reach the SQL instance. Cloud Run needs both: a working SQL login, plus IAM (roles/cloudsql.client, which the default Compute service account already has via roles/editor) to open the connection.

Step 4 — Secret Manager and the IAM detour

The two values our backend needs at runtime — the database URL (with the Postgres password embedded) and the JWT signing secret — are sensitive. We don’t want them in source control or in the Cloud Run service’s plain env vars, where anyone with read access to the service config could see them. Secret Manager is GCP’s answer: an encrypted store, accessed via IAM, that Cloud Run can mount as env vars at container boot.

Two secrets created:

# DATABASE_URL uses the Cloud SQL Unix-socket form, because Cloud Run
# attaches the SQL instance as a socket at /cloudsql/<CONN> rather than
# a TCP host.
DATABASE_URL="postgresql://torch:${PASSWORD}@localhost/torch?host=/cloudsql/${INSTANCE_CONN}&schema=public"

printf '%s' "$DATABASE_URL" | gcloud secrets create torch-database-url --data-file=-
printf '%s' "$JWT_SECRET"   | gcloud secrets create torch-jwt-secret   --data-file=-
A real footgun we hit

When pasting multi-line shell commands into zsh, the terminal can insert literal newlines inside quoted variables. We accidentally stored a DATABASE_URL with a \n in the middle, which would have failed silently in production. Always pipe a single-line printf '%s' and verify with echo "$DATABASE_URL" | cat -A — only one $ at the end means clean.

The IAM detour

Two principals need access to these secrets:

  1. You (the human) — to grant access. Needs roles/secretmanager.admin.
  2. The Cloud Run service account — to read the values at boot. Needs roles/secretmanager.secretAccessor.

Cloud Run runs as the default Compute service account: <PROJECT_NUMBER>-compute@developer.gserviceaccount.com. That account already has broad Editor on the project, which lets it create secrets but not access their values — Google deliberately split those permissions so a blanket Editor role can’t hand out secret reads. So we add secretAccessor explicitly.

The deployer (us) hit a permission wall here: Editor doesn’t include secretmanager.secrets.setIamPolicy either. Project owner had to grant Secret Manager Admin first. The two roles sound near-identical:

RoleCan
Secret Manager AdminManage secrets and grant access
Secret Manager Secret AccessorRead a secret’s value only

Once Admin landed, we bound the Compute SA to the Accessor role on each secret via the Secret Manager UI. Two clicks per secret.

Step 5 — Artifact Registry

Cloud Run needs to pull a Docker image from somewhere. Artifact Registry is GCP’s in-project image registry — private, fast pulls, no auth wiring required because Cloud Run is already in the same project. Cheaper and simpler than Docker Hub or GitHub Container Registry for this purpose.

gcloud artifacts repositories create torch \
  --repository-format=docker \
  --location=us-central1 \
  --description="Torch backend container images"

One repo per service is the typical convention; ours just holds backend for now and will hold backend-pdf-worker later.

Step 6 — Building the image with Cloud Build

The backend has an existing Dockerfile at backend/Dockerfile, but it requires the build context to be torch_product/ (the parent directory), because the backend declares a file-system dependency on a sibling workspace package: "@torch/core": "file:../packages/tea-core". The Docker context has to include both directories.

gcloud builds submit --tag assumes a Dockerfile at the root of the context, which we don’t have. So a thin cloudbuild.yaml at torch_product/cloudbuild.yaml just tells Cloud Build the right paths:

steps:
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-f', 'backend/Dockerfile', '-t', '${_IMAGE}', '.']
images:
  - '${_IMAGE}'
options:
  logging: CLOUD_LOGGING_ONLY

Then:

export IMAGE=us-central1-docker.pkg.dev/${PROJECT_ID}/torch/backend:v1
gcloud builds submit --config=cloudbuild.yaml --substitutions=_IMAGE=$IMAGE .

Cloud Build vs GitHub Actions — and why we picked Cloud Build

Both can build and push images. The deciding factor for a first deploy is wiring overhead. Cloud Build runs inside the GCP project and is already authenticated against Artifact Registry; gcloud builds submit works zero-config. GitHub Actions would have meant creating a service account, generating a JSON key, storing it as a GitHub secret, and writing a workflow file — fine for ongoing CI, overkill for the first push. We can wire Actions later if and when we want push-to-deploy.

Upload bloat

The first build uploaded 974 MB of tarball because gcloud zipped everything in torch_product/, including node_modules, dist, and the entire frontend. The image itself was only 181 MB. We added a .gcloudignore at torch_product/.gcloudignore so future uploads only ship the relevant source — same idea as .gitignore, but for gcloud.

Step 7 — Running Prisma migrations against Cloud SQL

The newly-created Cloud SQL database is empty. Prisma needs to apply the migrations in backend/prisma/migrations/ to create the tables. But: the database isn’t reachable on the public internet, and we don’t want it to be.

The standard pattern is to use the Cloud SQL Auth Proxy — a small Go binary that opens a local TCP port on 127.0.0.1:5432, authenticates to Cloud SQL using your gcloud credentials, and forwards traffic over a TLS tunnel to the instance. From the app’s point of view it’s just plain Postgres on localhost.

# Terminal 1: start the proxy
./cloud-sql-proxy project-688a4c78-5d5b-45b3-b5d:us-central1:torch-db

# Terminal 2: run the migration using a localhost DATABASE_URL
export DATABASE_URL="postgresql://torch:${PASSWORD}@127.0.0.1:5432/torch?schema=public"
npx prisma migrate deploy
Two different DATABASE_URLs

One for the proxy (TCP on localhost: ...@127.0.0.1:5432/torch), one for Cloud Run (Unix socket: ...@localhost/torch?host=/cloudsql/<CONN>). Same database, different paths in. Easy to mix up. The Unix socket form is the one stored in Secret Manager.

The proxy also needed gcloud auth application-default login — a different credential than gcloud auth login. ADC is the standard mechanism GCP client libraries use to authenticate; once set up, every tool on the machine inherits it.

Step 8 — Deploying to Cloud Run

The image is in Artifact Registry, the secrets are in Secret Manager, the database has tables. We wire it all together with one gcloud run deploy command — which we put in a shell script (backend/deploy.sh) because zsh kept mangling the line continuations when pasted:

gcloud run deploy torch-backend \
  --image="$IMAGE" \
  --region="$REGION" \
  --platform=managed \
  --allow-unauthenticated \
  --add-cloudsql-instances="$INSTANCE_CONN" \
  --set-secrets=DATABASE_URL=torch-database-url:latest,JWT_SECRET=torch-jwt-secret:latest \
  --set-env-vars=NODE_ENV=production,FRONTEND_URL=https://torch-snowy.vercel.app,COOKIE_SECURE=true \
  --port=8080 \
  --memory=512Mi \
  --cpu=1 \
  --min-instances=0 \
  --max-instances=3 \
  --timeout=60

Every flag, decoded:

FlagWhat it does, and why
--allow-unauthenticatedMakes the URL reachable from the public internet. Without this, every request needs a Google identity token — which a browser cannot provide. App-level JWT auth handles real security.
--add-cloudsql-instancesAttaches the Cloud SQL instance as a Unix socket at /cloudsql/<CONN>. The DATABASE_URL’s host= parameter points here.
--set-secretsInjects each Secret Manager secret as the named env var at container start. The :latest suffix means new secret versions are picked up on the next deploy.
--set-env-varsNon-sensitive env: production mode, CORS allowlist, cookie flag.
--memory=512Mi --cpu=1Smallest sensible footprint for a Node app. Easy to bump.
--min-instances=0Scale to zero when idle. The cold-start trade-off discussed earlier.
--max-instances=3Cost guardrail. Cloud Run autoscales between min and max; the max is just a ceiling to prevent runaway spikes from running up the bill. Default if omitted is 100.
--timeout=60Max time a request can take before Cloud Run kills it.

Step 9 — Making the service publicly invokable

The --allow-unauthenticated flag tries to set an IAM binding (allUsers → roles/run.invoker) on the service. That requires run.services.setIamPolicy, which Editor does not grant. So the deploy succeeded but the binding failed with a warning. The org owner granted Cloud Run Admin, and then:

gcloud run services add-iam-policy-binding torch-backend \
  --region=us-central1 \
  --member=allUsers \
  --role=roles/run.invoker
The mental model for the two IAM walls we hit

Editor is a broad role — it can do almost anything except grant access to others. That gate is intentionally separate for each service. So for any GCP service where you also need to manage who can reach it, you typically need that service’s Admin role in addition. We needed it twice: once for Secret Manager (to grant the Cloud Run SA secret access) and once for Cloud Run (to grant the world the ability to invoke the service).

Wiring the frontend to the backend

The last step is purely on the Vercel side. We added an environment variable to the Vercel project:

NEXT_PUBLIC_API_URL=https://torch-backend-746208330214.us-central1.run.app

Triggered a redeploy. The frontend now calls the live backend.

A few quiet details that worked out in our favor:

  • HTTPS: Cloud Run terminates TLS automatically with a Google-managed certificate. Nothing to configure.
  • Cookies were a non-issue because the backend uses Authorization: Bearer <token> rather than cookies. If it had used cookies, we’d have needed SameSite=None; Secure for the Vercel-domain → Cloud Run-domain cross-site path.
  • CORS: the backend reads FRONTEND_URL from env and configures cors({ origin }) accordingly. We set it to the Vercel URL; preview deployments at torch-snowy-<hash>.vercel.app would currently be blocked — a small thing to revisit when we use previews.

Living with the deploy — questions that come up after

Once the service is live, a handful of questions surface within the first week. Worth pinning them down now.

Does Cloud SQL keep running always? Should it?

Yes — Cloud SQL is a persistent VM that runs Postgres 24/7. Unlike Cloud Run, it doesn’t scale to zero, because a database is stateful and can’t simply disappear between requests. That’s where most of the ~$8/month bill comes from.

You can stop it manually if you know nobody (real users or you) will hit the backend for a while:

gcloud sql instances patch torch-db --activation-policy=NEVER   # stop
gcloud sql instances patch torch-db --activation-policy=ALWAYS  # start

While stopped, every request that touches the DB fails. Only useful as a knob for long off-periods on dev environments — for a production app you want available on demand, leave it on.

When does the image get rebuilt? Will the 974 MB upload happen every time?

The image only rebuilds when you choose to rebuild it — there’s no auto-trigger watching the repo. Specifically, you re-run gcloud builds submit only when:

  • Backend source under backend/src/** changed.
  • Backend dependencies in backend/package.json changed.
  • The Dockerfile, the Prisma schema, or the tea-core package changed.

Frontend changes, env-var tweaks, secret rotations — none of those require a rebuild. Cloud Run also doesn’t care about new frontend deploys on Vercel; they’re entirely separate services.

About the upload bloat: that 974 MB tarball was a one-time mistake from the first build before we had a .gcloudignore. Now that the file exists at torch_product/.gcloudignore, future uploads will exclude node_modules, dist, the frontend, and anything else not needed by the Docker context. Expect subsequent builds to upload only a few MB. You can confirm by watching the first line of the next build’s output:

Creating temporary archive of N file(s) totalling X MiB before compression.

Where does .env live, and how does the backend find its env vars in two different environments?

Three different worlds, three different sources of truth:

EnvironmentWhere env vars come from
Local dev
npm run dev		 A backend/.env file. dotenv reads it at startup and populates process.env. Has local-friendly defaults: localhost:5432, placeholder JWT secret, FRONTEND_URL=http://localhost:3001.
Cloud Build
(during builds submit)		 None. Builds just run docker build — nothing reads env vars at this stage. Secrets and config are not embedded in the image.
Cloud Run
(production runtime)		 No .env file inside the container. Cloud Run injects vars from --set-env-vars (plain) and --set-secrets (Secret Manager) directly as OS env vars at container start. dotenv finds no file, does nothing, and process.env is already populated.

The clean part of this design: src/config/env.ts is the same code in all three. It calls dotenv.config() (a no-op in Cloud Run since no file exists), then reads from process.env with safe defaults. Nothing downstream of env.ts knows or cares which environment is feeding it.

Two safety notes worth pinning to the wall:

  • .env is in .gitignore. It must never be committed. The committed .env.example is the template — anyone cloning the repo copies that file to .env and fills in their own local values.
  • Cloud Run’s env vars are visible in the GCP console to anyone with read access to the service. Anything sensitive (DB password, JWT secret) goes through Secret Manager, not --set-env-vars. That’s why DATABASE_URL and JWT_SECRET are bound from secrets and FRONTEND_URL / NODE_ENV are plain.

So how does the backend know which frontend URL to allow for CORS?

From a single variable, FRONTEND_URL, set in whichever environment you’re running in:

  • Locally: FRONTEND_URL=http://localhost:3001 from backend/.env.
  • On Cloud Run: FRONTEND_URL=https://torch-snowy.vercel.app from the --set-env-vars flag we passed at deploy.

The wiring is one line in src/app.ts:

app.use(cors({ origin: env.FRONTEND_URL, credentials: true }));

Same code, different env, different allowlist. To see what’s actually live in production right now:

gcloud run services describe torch-backend --region=us-central1 \
  --format='value(spec.template.spec.containers[0].env)'

To change it without rebuilding the image (e.g., when we map a custom domain):

gcloud run services update torch-backend --region=us-central1 \
  --set-env-vars=FRONTEND_URL=https://api.torch.lemnisca.bio

Cloud Run starts a new revision with the updated env and shifts traffic over. No image rebuild, no downtime.

CORS only matches the exact string

cors({ origin }) accepts a string or an array — and does an exact match. So https://torch-snowy.vercel.app passes, but Vercel preview URLs like https://torch-snowy-git-feature-xyz.vercel.app get blocked. Not an issue today, but if we want preview deployments to talk to the backend later, swap origin for a regex-based function that allows the production URL, all preview subdomains, and localhost. Trivial to add when needed.

Redeploying after code changes (the everyday flow)

The initial deploy is one-time. The flow you’ll repeat dozens of times is: pull a code change, decide whether anything needs to be rebuilt, redeploy. This section is the cookbook.

1. The frontend vs. backend split

Frontend changes never touch GCP. Vercel and Cloud Run are independent — push to your frontend branch, Vercel rebuilds, done. The only time order matters is when a frontend change depends on a new backend endpoint that hasn’t been deployed yet: in that case, deploy the backend first, then merge the frontend.

2. Pulling and merging a remote branch into main

Common starting state: someone pushed a branch on the remote (say, new_our_method) that you want to integrate. You may also have uncommitted local work. Don’t panic — the safe sequence is:

Handle local untracked / modified files first

Untracked files (new files git isn’t watching) don’t block a merge unless the incoming branch tries to create the same path. Still, before merging, you want a clean working tree so you’re not mixing your changes with someone else’s. Three options:

  • Commit them if they belong in the repo (configs, source, docs).
  • Add them to .gitignore if they’re local-only artifacts (binaries, build output, the cloud-sql-proxy binary, etc.).
  • Stash if they’re half-done work: git stash push -u -m "wip". Restore later with git stash pop.

For modified-but-not-committed files, same options — git stash is the lightest. Verify with:

git status

You want it to say either “nothing to commit, working tree clean” or “only untracked files that don’t collide with the merge.”

Fetch and merge

git fetch origin
git branch -a | grep new_our_method      # confirm origin/new_our_method exists locally
git checkout main
git pull origin main                     # make sure local main is current
git merge origin/new_our_method

If git auto-merges, you’re done — push:

git push origin main

If git reports conflicts, it lists the conflicting files. Open each, resolve the <<<<<<< markers, then:

git add <resolved-files>
git commit
git push origin main

3. Decide whether you need to rebuild the Docker image

Rebuilding is the only expensive step (a few minutes) and the only one that pushes a new image to Artifact Registry. You only need to do it when the things that go into the image have changed:

  • Anything in backend/src/** — your Express code.
  • backend/package.json or package-lock.json — new or updated dependencies.
  • The Dockerfile itself.
  • backend/prisma/schema.prisma — Prisma generates new client code at build time.
  • Anything under packages/tea-core/** — the backend imports it as @torch/core via a file: dependency, so it’s baked into the image.

Quick way to inspect what just changed:

git diff HEAD~1 HEAD -- torch_product/backend torch_product/packages/tea-core

Empty output → no rebuild needed. Anything in there → rebuild. Pure frontend or doc changes never trigger a backend rebuild.

4. Rebuild and redeploy

From torch_product/, bump the image tag (so you can roll back) and run the same two commands as the initial deploy:

cd /Users/kartikey/Desktop/torch/torch_product

export PROJECT_ID=project-688a4c78-5d5b-45b3-b5d
export REGION=us-central1
export INSTANCE_CONN=project-688a4c78-5d5b-45b3-b5d:us-central1:torch-db
export IMAGE=us-central1-docker.pkg.dev/${PROJECT_ID}/torch/backend:v2   # bump v1 → v2 → v3 ...

# Build + push to Artifact Registry
gcloud builds submit --config=cloudbuild.yaml --substitutions=_IMAGE=$IMAGE .

# Deploy the new image to Cloud Run
bash backend/deploy.sh

Cloud Run creates a new revision (e.g. torch-backend-00003-tvt) and shifts 100 % of traffic to it once it’s healthy. The old revision sticks around so you can roll back instantly.

Confirm it’s live

curl https://torch-backend-746208330214.us-central1.run.app/api/health

Should return {"status":"ok","timestamp":"..."} with a fresh timestamp.

Roll back if something’s broken

List revisions:

gcloud run revisions list --service=torch-backend --region=us-central1

Send all traffic back to the previous one:

gcloud run services update-traffic torch-backend --region=us-central1 \
  --to-revisions=<previous-revision-name>=100

No image rebuild, no downtime — Cloud Run just re-routes.

5. Did the Prisma schema change? Run migrations.

If the merge touched backend/prisma/schema.prisma and added a new migration file under backend/prisma/migrations/, you have to apply that migration to Cloud SQL before the new code starts running — otherwise the new code looks for columns or tables that don’t exist and crashes.

Same flow as the original migration step: start the proxy, set a localhost-pointed DATABASE_URL, run prisma migrate deploy.

# Terminal 1
cd /Users/kartikey/Desktop/torch/torch_product
./cloud-sql-proxy project-688a4c78-5d5b-45b3-b5d:us-central1:torch-db

# Terminal 2
cd /Users/kartikey/Desktop/torch/torch_product/backend
export DB_PASSWORD='<the-real-password>'
export DATABASE_URL="postgresql://torch:${DB_PASSWORD}@127.0.0.1:5432/torch?schema=public"
npx prisma migrate deploy

Run migrations before deploying the new image when the schema change is breaking (renaming columns, removing tables). For additive changes (new nullable column, new table), order is more forgiving but the same sequence is still the safe habit.

6. Frontend-only changes — no GCP work at all

Push to the frontend repo / branch that Vercel watches; Vercel auto-rebuilds. The backend keeps running unchanged. The only thing that ties them is the NEXT_PUBLIC_API_URL env var on Vercel pointing at the Cloud Run URL — which doesn’t move unless we change Cloud Run’s service name or map a custom domain.

The mental shortcut

backend/src/**, backend/package.json, the Dockerfile, the Prisma schema, or packages/tea-core/** changed → rebuild image + redeploy. Schema migration added → run prisma migrate deploy against Cloud SQL too. Everything else → no GCP work.

What’s still left

The backend is live and serving traffic, but the deploy story isn’t fully “done” in the long-term sense. In rough order of importance:

  1. Set a billing budget alert. Three minutes in the GCP console; catches runaway costs (bugs, abuse) before they become real money.
  2. Map a custom domain like api.torch.lemnisca.bio — cleaner and decouples the URL from any specific deploy.
  3. Rate limiting. Cloud Run doesn’t throttle anything by itself; an express-rate-limit middleware is a few lines of code.
  4. Push-to-deploy. A Cloud Build trigger (or GitHub Action) that builds and deploys on every push to main.
  5. Firebase Auth swap. The original architecture plan; the current bcrypt+JWT works fine and can be migrated later.
  6. PDF generation worker. Explicitly deferred — separate Cloud Run service, Cloud Tasks queue, Cloud Storage bucket.

A note on cost

At rest, this whole stack should sit at roughly:

ComponentApprox. monthly cost
Cloud SQL db-f1-micro (always on)~$8
Cloud Run (min-instances=0, idle)$0
Artifact Registry storage (one image, ~180 MB)< $0.01
Secret Manager (two secrets)$0 (under free tier)
Cloud Build (first build was free; subsequent builds are ~$0.003/min)~$0.10/mo
Cloud Logging$0 at low volume
Total at idle~$8

Traffic-driven costs are the only thing that grows from here, and at our user scale they won’t move the needle. The dominant cost will remain Cloud SQL — and the cheapest way to halve it once the app is on real users is to switch the instance to “Zonal” (single zone, no HA) which it already is by default, and keep storage-auto-increase on so we never over-provision disk.

That’s the whole walkthrough. If you’re repeating this for a sibling service (the PDF worker, eventually), the only steps that change are: a new Artifact Registry image name, a new Cloud Run service, and the env vars / secrets it needs. Everything else — project, region, SQL instance, IAM bindings — is shared.
